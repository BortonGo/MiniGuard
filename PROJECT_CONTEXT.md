# MiniGuard Project Context

Этот документ хранит исходную идею проекта и правила совместной разработки. Его
нужно читать вместе с [`ROADMAP.md`](ROADMAP.md): здесь описано **зачем и как** мы
строим MiniGuard, а в roadmap — **где мы сейчас находимся**.

## Идея проекта

MiniGuard — учебный Linux Endpoint Security Agent на C++20. Это небольшой
pet-project в области endpoint security, а не попытка создать коммерческий
антивирус.

Главная цель — научиться системному программированию под Linux настолько хорошо,
чтобы владелец проекта мог самостоятельно объяснить:

- архитектуру программы;
- используемые Linux-механизмы;
- путь данных между userspace и kernel space;
- принятые проектные решения и их компромиссы;
- методы отладки, тестирования и измерения производительности.

Проект должен стать сильной учебной работой для стажировки или Junior C++ позиции,
в том числе в компании, занимающейся endpoint security.

## Что должно получиться

В финальном состоянии MiniGuard демонстрирует:

- Linux filesystem monitoring;
- process и execution monitoring;
- самостоятельный разбор ELF64;
- простой безопасный scanner и rule engine;
- quarantine;
- Unix Domain Socket IPC между CLI и daemon;
- многопоточность;
- взаимодействие userspace с учебным kernel module;
- тестирование, debugging и profiling.

Количество функций вторично. Корректность, безопасность и понимание каждой
существенной части важнее.

## Учебный контракт

Мы не пишем проект целиком за владельца. Для каждой новой системной части работа
идёт в таком порядке:

1. Сформулировать решаемую проблему.
2. Объяснить соответствующий Linux-механизм.
3. Показать архитектуру или поток данных.
4. Разобрать нужные Linux API, syscalls и возможные ошибки.
5. Предложить владельцу самостоятельно написать небольшую центральную часть.
6. Проверить его попытку и объяснить проблемы.
7. При необходимости усиливать помощь постепенно: подсказка → псевдокод → часть
   реализации → полное решение.
8. Проверить результат инструментами и вопросами на понимание.

Boilerplate, CMake, Git-настройки и небольшие вспомогательные конструкции можно
готовить полностью, если в них нет важной учебной ценности. Даже в этом случае
нужно кратко объяснять их назначение.

Если появляется Linux API вроде `open()`, недостаточно показать вызов. Нужно
понимать:

- что такое file descriptor и кому он принадлежит;
- как libc вызывает syscall;
- что происходит между userspace, kernel, VFS и filesystem driver;
- какие ошибки возвращаются через `errno`;
- кто владеет ресурсом и почему его нужно освободить.

## Рабочая среда

Основная среда исполнения — полноценная Ubuntu VM в Hyper-V. Mac и Windows
подключаются к ней через VS Code Remote SSH. Сборка, запуск, отладка, fanotify,
procfs и kernel module выполняются в Linux.

Dev Containers и WSL не заменяют эту VM в текущей архитектуре. Подробности и
актуальные адреса находятся в [`docs/environment.md`](docs/environment.md).

## Ориентировочная архитектура

```text
                 ┌────────────────────┐
                 │    miniguard-cli   │
                 └─────────┬──────────┘
                           │ Unix Domain Socket
                           ▼
                 ┌────────────────────┐
                 │  miniguard-daemon  │
                 └─────────┬──────────┘
                           │
          ┌────────────────┼────────────────┐
          │                │                │
          ▼                ▼                ▼
   File Monitor      Process Monitor      Scanner
     fanotify            procfs         Rule Engine
          │                │                │
          └────────────────┼────────────────┘
                           ▼
                       Quarantine
                           │
                    optional later
                           ▼
                    /dev/miniguard
                           │
                           ▼
                    miniguard.ko
```

Это ориентир, а не обязательная финальная схема. Архитектура должна расти вместе с
проектом; нельзя заранее создавать лишние слои и каталоги.

## Технические принципы

Userspace-код:

- C++20;
- CMake и Ninja/Make;
- RAII для владения ресурсами;
- smart pointers только при реальной необходимости;
- `std::filesystem`, `std::span`, `std::string_view`, `std::optional` и другие
  современные типы — когда они упрощают дизайн;
- прямое изучение POSIX/Linux API вместо сокрытия системных механизмов;
- небольшой RAII wrapper для file descriptor после понимания ручного lifecycle;
- без сложного template metaprogramming и паттернов ради паттернов.

Правила и компоненты должны быть разделены по ответственности. Например,
`RuleEngine` не должен быть набором случайных `if` внутри scanner, но dependency
inversion не нужно применять там, где он не даёт практической пользы.

## Безопасные границы

- Не использовать настоящие вредоносные программы.
- Для scanner применять искусственные правила и безопасные тестовые файлы; EICAR —
  только когда это уместно и контролируемо.
- Не реализовывать rootkit-like функциональность, скрытие процессов, syscall
  hooking, обход средств защиты или persistence.
- Kernel module нужен только для изучения driver/kernel API: init/exit, character
  device, read/write/ioctl и безопасная статистика.
- Не усложнять file monitor блокировкой событий, пока корректно не работает режим
  наблюдения.

## Testing, debugging и performance

Тесты добавляются вместе с компонентами. Особенно важны тесты для ELF parser,
rule engine, scanner, hash, `/proc` parser и IPC serialization. Linux integration
tests могут быть отделены от unit tests.

На протяжении проекта используются:

- GDB;
- strace и ltrace;
- Valgrind;
- AddressSanitizer;
- UndefinedBehaviorSanitizer.

Недостаточно просто запустить инструмент: нужно понимать, на каком уровне он
работает и что именно показывает.

Performance изучается только после появления корректной версии:

```text
make it correct → measure → optimize
```

помощь в формулировке сильного ответа.

## Git workflow

- Перед началом работы: `git pull --ff-only`.
- Одна логическая задача — один commit.
- Перед `git add` обязательно смотреть `git status`.
- Вместе с кодом обновлять тесты, заметки и соответствующие пункты roadmap.
- Commit messages должны объяснять изменение, например:
  - `feat: add fanotify filesystem monitor`;
  - `test: add rule engine tests`;
  - `refactor: introduce FileDescriptor RAII wrapper`;
  - `docs: describe Linux VFS basics`.
- После проверенной рабочей сессии выполнять `git push`, чтобы состояние было
  доступно с Mac и Windows.

## Как начинать новую сессию с помощником

1. Прочитать `PROJECT_CONTEXT.md`.
2. Прочитать блок **Текущий фокус** и последние записи в `ROADMAP.md`.
3. Проверить `git status` и не перезаписывать чужие изменения.
4. Продолжить только текущий этап, не перескакивая вперёд.
5. Сначала объяснить задачу, затем дать владельцу небольшую самостоятельную часть.
